## 2. Database Schema Summary

Schema file: `prisma/schema.prisma` (339 lines). All money fields use `Decimal @db.Decimal(12,2)`; all quantity fields use `Float` (see §4.2 for why, and the precision caveat).

### Enums
- `Role`: `ADMIN`, `CASHIER`, `MANAGER`
- `PaymentMethod`: `CASH`, `CARD`, `CHEQUE`, `BANK_TRANSFER`
- `ChequeStatus`: `PENDING`, `CLEARED`, `BOUNCED`, `CANCELLED`
- `OrderStatus`: `DRAFT`, `ORDERED`, `PARTIAL`, `RECEIVED`, `CANCELLED`

Note: `Bill.status`, `PurchaseOrder.paymentStatus`, `StockMovement.type`, and `StockMovement.purpose` are all plain `String` fields (not enums), documented only by inline comments (e.g. `// PENDING | PAID | PARTIAL | CANCELLED`). Nothing at the database level prevents an invalid string being written to these columns.

### NextAuth models
`Account`, `Session`, `VerificationToken` — standard NextAuth Prisma adapter shape, each tied to `User` via cascading foreign keys.

### Core models and relationships

- **`User`** — `id, name?, email (unique), password?, role (default CASHIER), ...`. Has many `Bill` (the cashier/staff member who issued each sale).
- **`Customer`** — `id, name, nic? (unique), phone?, email? (unique), address?`. Has many `Bill`, `Payment`, `Cheque`.
- **`Supplier`** — `id, name, phone?, email? (unique), address?`. Has many `PurchaseOrder`, `SupplierPayment`.
- **`Item`** (product/inventory master) — `barcode (unique), name, category?, unit (default "pcs"), stockQty (Float, default 0), reorderLevel (Int, default 5), buyingPrice (Decimal), sellingPrice (Decimal)`. Has many `BillItem`, `PurchaseItem`, `StockMovement`, `PurchaseBatch`.
- **`Bill`** (invoice/sale header) — belongs to one `User` (required) and optional `Customer` (walk-in sales allowed). Money fields: `subtotal, discount, tax, totalAmount, amountPaid`. Has many `BillItem`, `Payment`, `Cheque`.
- **`BillItem`** (invoice line) — `quantity (Float), returnedQty (Float, default 0), unitPrice, buyingPrice (cost snapshot at sale time, for margin reporting), batchId? (String), discount, totalPrice`. Belongs to `Bill` (cascade delete) and `Item`.
  - **Important:** `batchId` is a bare `String?` — there is **no Prisma `@relation`** wiring it to `PurchaseBatch.id`. It is a soft pointer resolved manually in application code, not an enforced foreign key.
- **`Payment`** — customer payment against a `Bill`. `amount, method (PaymentMethod, default CASH), reference?, paidAt`.
- **`Cheque`** — customer cheque against a `Bill` (distinct model from `SupplierCheque`). `chequeNumber, bank, amount, chequeDate, depositDate?, status (ChequeStatus)`. **See §5 — this model has no working write path anywhere in the codebase.**
- **`PurchaseOrder`** — supplier purchase/delivery header. `orderNumber (unique), status (OrderStatus, default DRAFT), paymentStatus (String, default "UNPAID"), totalAmount, amountPaid`. Has many `PurchaseItem`, `SupplierPayment`.
- **`PurchaseItem`** — PO line item. `quantity (Float), unitCost, totalCost, receivedQty (Float, default 0)`.
- **`SupplierPayment`** — outgoing payment to a supplier against a `PurchaseOrder`. `amount, method (PaymentMethod), reference?`. Has one optional `SupplierCheque` (1:1, enforced via `@unique` on `SupplierCheque.supplierPaymentId`).
- **`SupplierCheque`** — cheque details for a `SupplierPayment`. `chequeNumber, bank, amount, chequeDate, passedDate? (set when cleared), status (ChequeStatus, default PENDING)`.
- **`StockMovement`** — inventory audit ledger. `itemId, type (String: "SALE" | "RETURN" | "MIXING"), quantity (Float, signed — negative for consumption, positive for restock/return), purpose? (used for MIXING entries)`.
- **`PurchaseBatch`** — FIFO cost-lot/batch tracking for an `Item`. `quantity (original batch qty), remainingQty (live remaining), buyingPrice, sellingPrice (batch-specific — can differ across batches of the same Item), createdAt`.

### Relationship diagram (textual)

```
User ──1:N── Bill ──1:N── BillItem ──N:1── Item ──1:N── PurchaseBatch
 │              │                              ├──1:N── PurchaseItem ──N:1── PurchaseOrder ──N:1── Supplier
 │              ├──1:N── Payment                                       ├──1:N── SupplierPayment ──1:1── SupplierCheque
 │              └──1:N── Cheque (unused, see §5)              Item ──1:N── StockMovement
Customer ──1:N── Bill, Payment, Cheque
```

## 3. Implemented Features (Dashboard Modules → API Routes)

All frontend pages live under `src/app/(dashboard)/`. All backend logic lives under `src/app/api/` (Next.js App Router route handlers — **no dynamic `[id]` segments exist anywhere**; updates go through body/query params on collection routes or dedicated action sub-routes like `/pass`, `/return`, `/settle`).

### Billing / POS
`src/app/(dashboard)/billing/page.tsx` (client component, ~805 lines)
- Loads catalog via `GET /api/items` — confirmed wired: the API explodes each `Item` into one catalog row **per active `PurchaseBatch`**, so the same product can appear multiple times at different batch prices/stock levels.
- Cart state is local React state, mirrored to `localStorage` for draft recovery on refresh.
- Simulated barcode scanning via a global keydown listener that accumulates characters until `Enter`, matched against the catalog by barcode.
- Checkout calls `POST /api/bills` — confirmed wired: `src/app/api/bills/route.ts` processes the request in one `prisma.$transaction`, creating the `Bill`, per-line `BillItem`s (via FIFO or manual batch selection, see §4.3), and a `Payment` row.
- Returns: `GET /api/bills/return?billNumber=...` fetches an original invoice and server-computes `availableToReturn = quantity - returnedQty` per line; selected quantities are pushed back through `POST /api/bills` as negative-quantity `isReturn` line items. The "Process Customer Return" button is hidden for the `CASHIER` role client-side.
- Quick customer creation inline from the cart via `POST /api/customers`.
- Checkout is blocked if any cart line is priced below its `buyingPrice` (loss-prevention guard).
- Receipt "printing" is `window.print()` against a hidden 80mm-styled `print:block` div — no PDF/thermal-printer SDK integration.

### Inventory
`src/app/(dashboard)/inventory/{page.tsx, InventoryClient.tsx, InventoryTable.tsx, AddItemForm.tsx, MixingButton.tsx}`
- Listing page is a **server component** querying `prisma.item.findMany` directly (no client fetch for the initial list).
- New items: `POST /api/items` — confirmed wired, validates barcode/name/prices and rejects duplicate barcodes with 409.
- Low-stock badge computed client-side as `item.stockQty <= item.reorderLevel` (per-item configurable threshold).
- Paint Mixing feature (shown only for items whose `category` contains "paint"): `MixingButton.tsx` opens a modal to pick a purpose/quantity/note, calling `POST /api/items/mixing` — confirmed wired, consumes stock FIFO across `PurchaseBatch` rows and logs a `StockMovement` (`type: "MIXING"`).
- `mixing-history/page.tsx` (server component) lists `StockMovement` rows where `type: "MIXING"` with search/date/purpose filters and pagination.
- No generic stock-adjustment / write-off / damage-correction UI exists anywhere — stock only changes via restock, sale, mixing, or return.

### Customers
`src/app/(dashboard)/customers/page.tsx`
- Full CRUD: `GET/POST/PUT/DELETE /api/customers` — all confirmed wired. `GET` computes `totalDebt` server-side as `Σbills - Σpayments`, floored at 0, with search (name/phone/nic) and pagination.
- Delete is a **hard delete** with a native `confirm()` — no soft-delete/archival, and no cascade is defined on `Bill.customer`, so deleting a customer with existing bills relies on Prisma's default FK behavior.
- "Receive Cash" (shown only if debt > 0) → `POST /api/payments/settle` — confirmed wired: applies cash across the customer's bills oldest-first, recomputing real per-bill debt from the `Payment` ledger rather than trusting `Bill.status`/`amountPaid`.

### Suppliers
`src/app/(dashboard)/suppliers/{page.tsx, AddSupplierForm.tsx}`
- `GET/POST /api/suppliers` — confirmed wired. `GET` computes `totalDebt` per supplier as `Σ max(0, order.totalAmount - order.amountPaid)` across their purchase orders.
- "Issue Payment" (shown only if debt > 0) → `POST /api/suppliers/settle` — confirmed wired: applies cash FIFO oldest-PO-first, `method` hardcoded to `"CASH"` in this flow (no cheque option in the settlement modal itself, unlike the restock form).
- Cheque status views (pending/cleared/bounced) live on the **Reports** page, not here.

### Purchase Orders / Restock
`src/app/(dashboard)/purchase-orders/{page.tsx, RestockForm.tsx}`
- `page.tsx` is a server component fetching suppliers + items directly via Prisma, passed into `RestockForm.tsx` (client, ~640 lines).
- This screen is purely a **receiving** flow — there is no create-draft → approve → receive lifecycle. Submission calls `POST /api/restock` — confirmed wired: creates `PurchaseOrder` (immediately `status: "RECEIVED"`) + `PurchaseItem`s, creates a `SupplierPayment` (supporting `CASH`, `CHEQUE`, or `MIXED` split, with a `SupplierCheque` row when applicable), increments `Item.stockQty`, overwrites `Item.buyingPrice`/`sellingPrice` with the latest restock values, and **creates a new `PurchaseBatch` row per item** — this is the sole batch-creation entry point in the system.
- Cheque-clash check: "Check other cheques available on this day" calls `GET /api/cheques/by-date?date=...` to warn if multiple supplier cheques already fall due on the selected date.
- Unknown barcode during restocking opens a modal to register a new `Item` on the fly (`POST /api/items`) before continuing.
- **`POST /api/purchase-orders`** (`src/app/api/purchase-orders/route.ts`) implements a separate, nearly-identical PO creation flow but is called from **nowhere in the frontend** (confirmed via repo-wide search) — see §5.

### Reports (ADMIN only)
`src/app/(dashboard)/reports/page.tsx` (~1560 lines, largest page in the app)
- Single aggregator endpoint: `GET /api/reports?range=&stockRange=&supplierId=&chequeSearch=&chequeDate=` — confirmed wired, server-side ADMIN-only check (`session.user.role !== "ADMIN"` → 401).
- Sections rendered: revenue-vs-debt bar chart (`recharts`); supplier stock report (POs in range, optionally filtered by supplier); low-stock items (**hardcoded `stockQty <= 5`**, top 5 — inconsistent with the per-item `reorderLevel` used by Inventory/Dashboard, see §5); top 5 debtors (computed in-memory from the bill/payment ledger); supplier cheque management with status badges and actions (`PATCH /api/cheques/pass` → `CLEARED`, `PATCH /api/cheques/return` → `BOUNCED`); daily bills report with computed final profit (`Σ(unitPrice - buyingPrice) * qty - discount`); returned-items report (bills containing negative-quantity `BillItem`s); upcoming-cheque alert banner (pending cheques due within 2 days).
- All sub-report tables are paginated via client-side `.slice()` over the entire array returned by the one API call — not server-side `skip`/`take` pagination.
- "Export PDF" (`exportPDF`) is literally `window.print()` — no real PDF generation library is used.

### Payments Ledger
`src/app/(dashboard)/payments/page.tsx` — pure **server component**, no client fetch. Queries `prisma.payment.findMany` and `prisma.supplierPayment.findMany` in parallel and renders two read-only side-by-side tables (customer inflows, supplier outflows). No settlement actions here — those live on the Customers/Suppliers pages. Includes a try/catch fallback banner if Prisma throws.

### Staff Management (ADMIN only)
`src/app/(dashboard)/users/page.tsx` — create-and-list only. `GET/POST /api/users` — confirmed wired (POST hashes password with bcrypt, rejects duplicate email). **No edit, delete, or deactivate functionality exists**, either in the UI or as an API route (no PUT/DELETE under `/api/users`). Role options are just labels (`CASHIER`/`MANAGER`/`ADMIN`); actual enforcement happens entirely via `middleware.ts` + the sidebar's role filter, not this page.

### Auth & Routing
- `src/app/page.tsx` — login form, `signIn("credentials", ...)`.
- `src/lib/auth.ts` — NextAuth `authOptions`: `CredentialsProvider.authorize()` looks up `User` by email, `bcrypt.compare`s the password, JWT session strategy, `jwt`/`session` callbacks propagate `id` and `role`.
- `src/middleware.ts` — role-based page-route guard (`withAuth`): `/dashboard`, `/users`, `/reports` → ADMIN only; `/inventory`, `/purchase-orders`, `/suppliers`, `/payments` → ADMIN or MANAGER; `/customers`, `/billing` → any authenticated role. Root `/` redirects by role after login (ADMIN→`/dashboard`, MANAGER→`/inventory`, else→`/billing`).
- **This middleware only covers page routes, not `/api/*`** — see §5 for the resulting authorization gap.

## 4. Core Business Logic

### 4.1 Point-of-Sale billing and cart calculations — *Partially implemented*

Implemented in `src/app/(dashboard)/billing/page.tsx` (client-side calculation) and `src/app/api/bills/route.ts` (server-side persistence), the latter wrapped entirely in one `prisma.$transaction`.

- **Client-side math**: `subtotal = Σ (overridePrice ?? price) × quantity`; `discount` is a single flat currency amount typed by the cashier (not a percentage); `finalTotal = subtotal − discount`. Live margin tracking (`grossProfit`, `marginPercent`) is computed in the browser, and checkout is disabled if any line's sale price is below that line's `buyingPrice`.
- **Server-side trust boundary**: `POST /api/bills` writes `subtotal, discount, tax, totalAmount, amountPaid` **directly from the request body** — there is no server-side recomputation of these totals against the persisted `billItems`. The client is fully trusted for the invoice's monetary summary.
- **Tax is schema-present but functionally dead**: `Bill.tax` exists in the database and is accepted by the API, but the billing UI has no tax input or calculation anywhere — `tax` is always sent as `0`/undefined.
- **`status` and `amountPaid` inconsistency at creation**: every bill is created with `status: "PAID"` hardcoded, regardless of whether `amountPaid < totalAmount` (i.e., even a credit/debt sale is marked "PAID" at the row level). `Bill.amountPaid` is **not set** in the `tx.bill.create()` call, so it remains at its schema default of `0` even though a corresponding `Payment` row is created for the actual amount tendered. Downstream code is aware of this and works around it: `POST /api/payments/settle` explicitly recomputes real debt from the raw `Payment` ledger sum rather than trusting `Bill.status`/`amountPaid` (comment in that route: "We no longer trust the status text. We trust the raw math.").
- **Payment method**: the billing UI never exposes a payment-method selector, so every `Payment.method` defaults to `CASH` in practice, even though the `PaymentMethod` enum supports `CARD`/`CHEQUE`/`BANK_TRANSFER`.
- Returns are handled through the same endpoint via an `item.isReturn` flag on submitted line items (see §3).

### 4.2 Fractional / decimal quantity billing system — *Fully implemented (data + UI layer)*

Introduced in commit `515ef57` ("feat: enable decimal quantities for bulk inventory and billing").

- Quantity-bearing fields were changed from `Int` to **`Float`** across the schema: `Item.stockQty`, `BillItem.quantity`/`returnedQty`, `PurchaseItem.quantity`/`receivedQty`, `StockMovement.quantity`, `PurchaseBatch.quantity`/`remainingQty`.
- Note this is `Float` (IEEE-754 double), **not** `Decimal` — unlike every money field, which remains fixed-point `Decimal(12,2)`. Quantity math is therefore subject to floating-point precision drift, while currency math is not.
- Frontend inputs were switched from integer-only controls to `<input type="number" step="any" min="0">` combined with `parseFloat` (not `parseInt`) in three places: the billing cart's quantity editor, the return-quantity editor, and the restock form's quantity input.
- **No unit-aware validation or rounding exists.** `Item.unit` (default `"pcs"`) is a free-text display label only — nothing prevents selling `2.5` units of an item whose unit is "pcs", and no rounding is applied before quantities are persisted (currency values use `.toFixed(2)` for display; quantities do not have an equivalent safeguard).

### 4.3 FIFO inventory deduction and batch management — *Fully implemented*

- Batch model: `PurchaseBatch` (`itemId, quantity, remainingQty, buyingPrice, sellingPrice, createdAt`). **Only `POST /api/restock` creates `PurchaseBatch` rows** — one per received line item. The parallel `POST /api/purchase-orders` endpoint increments `Item.stockQty`/`buyingPrice` but does **not** create batches (see §5), so FIFO/batch pricing only applies to stock entered through the restock flow.
- **FIFO consumption**, in `src/app/api/bills/route.ts`: batches for the sold item are fetched with `orderBy: { createdAt: "asc" }` (oldest first) and depleted via a loop that takes `Math.min(remainingQty, batch.remainingQty)` from each batch in turn until the requested sale quantity is satisfied, spilling into the next batch when one is exhausted. If quantity remains after all batches are consumed, the sale falls back to "legacy" (pre-batch) stock at the item's current `sellingPrice`/`buyingPrice`.
- **Manual override path**: the cashier can bypass default FIFO ordering and select a specific batch directly (surfaced in the billing UI as a "Select Batch Price" popup when multiple batches of the same barcode exist, since batches can carry different prices) — FIFO is the default consumption order, not the only one.
- The identical FIFO batch-consumption algorithm is reused in `POST /api/items/mixing` for internal stock consumption (paint mixing), decrementing batches oldest-first before decrementing `Item.stockQty`.
- Every deduction or restoration (sale, return, mixing) writes a corresponding `StockMovement` audit row with a signed `quantity` and a `type` of `SALE`, `RETURN`, or `MIXING`.

### 4.4 Supplier payments and cheque status management — *Fully implemented (supplier side); customer-side `Cheque` is dead code*

Two separate cheque models exist in the schema: `SupplierCheque` (tied 1:1 to a `SupplierPayment`) and `Cheque` (tied to a customer `Bill`).

- **Supplier-side (working)**: `SupplierCheque` rows are created during purchase intake by `POST /api/restock` or `POST /api/purchase-orders`, always starting at `status: "PENDING"`. Status transitions:
  - `PATCH /api/cheques/pass` → sets `status: "CLEARED"` and stamps `passedDate`.
  - `PATCH /api/cheques/return` → sets `status: "BOUNCED"`.
  - No route ever sets `status: "CANCELLED"`, despite it being a defined enum value.
  - `GET /api/cheques/by-date` lists pending supplier cheques due on a given date (used for cash-flow clash warnings during restocking); `GET /api/reports` also surfaces a cheque report and an "upcoming cheque" alert (pending, due within 2 days).
- **Supplier payment ledger (working)**: `POST /api/suppliers/settle` applies a cash amount across a supplier's oldest unpaid/partial `PurchaseOrder`s first, computing real outstanding debt as `totalAmount − Σ supplierPayments.amount` (ignoring the stored `paymentStatus` text) inside a `prisma.$transaction`, updating `PurchaseOrder.amountPaid`/`paymentStatus` and inserting a `SupplierPayment` row per order touched. The customer-side `POST /api/payments/settle` mirrors this exact pattern for `Bill`/`Payment`.
- **Customer-side `Cheque` model (not a working feature)**: a repository-wide search for any create/update against the `Cheque` Prisma model (as distinct from `SupplierCheque`) returns zero results. The only reference to it anywhere is a read-only `include: { cheques: true }` on the reports API's daily-bills query, which will therefore always return an empty array. The billing UI has no cheque-payment flow for customers, consistent with it also having no payment-method selector at all (see §4.1).
- **`PurchaseOrder.status` (`OrderStatus`) is effectively unused as a workflow**: only `"RECEIVED"` is ever written by either purchase-intake route; `DRAFT`, `ORDERED`, `PARTIAL`, and `CANCELLED` are never assigned anywhere in the codebase, so there is no draft/approve/partial-receive lifecycle despite the enum modeling one. The separate `paymentStatus` string field *is* actively driven through `UNPAID`/`PARTIAL`/`PAID`.

## 5. Unimplemented / Missing Features and Logical Gaps

- **Dead "Settings" nav link** — `src/app/(dashboard)/layout.tsx` renders a sidebar link to `/settings` for the ADMIN role, but no such route or page exists anywhere in `src/app`; clicking it 404s.
- **Orphaned API route** — `POST /api/purchase-orders` (`src/app/api/purchase-orders/route.ts`) is a fully implemented, alternate PO-creation handler with zero frontend callers anywhere in the repo. It diverges from the actually-used `/api/restock` in a meaningful way: it does not create `PurchaseBatch` rows, so any data created through it (if ever called directly, e.g. via API testing tools) would silently bypass FIFO batch tracking.
- **Customer-facing `Cheque` model is schema-only** — defined in `schema.prisma`, included (read-only, always empty) in one report query, but has no create/update code path anywhere. Not a working feature despite existing in the data model.
- **No purchase-order lifecycle** — the `OrderStatus` enum (`DRAFT`/`ORDERED`/`PARTIAL`/`CANCELLED`) is defined but never assigned; every purchase order is created already `RECEIVED`. There is no draft → approval → partial-receipt workflow anywhere in the UI or API.
- **No tax logic in the billing UI** — `Bill.tax` exists in the schema and is round-tripped by the bills API, but nothing in `billing/page.tsx` computes, displays, or sends a nonzero tax value.
- **Bill `status`/`amountPaid` unreliable at creation** — every bill is hardcoded to `status: "PAID"` and `amountPaid` is left at its default `0` regardless of what was actually paid; correctness is only restored later by ledger-recomputation logic in `/api/payments/settle`, rather than being correct at the point of creation.
- **No stock-adjustment / write-off / damage-correction UI** — the Inventory module has no manual stock-correction form; stock can only change via restock, sale, mixing, or return.
- **`ChequeStatus.CANCELLED` is never reachable** — the enum defines it, but no route transitions any cheque to that status.
- **Missing API-level authorization on numerous routes** — `getServerSession` is called only in `bills`, `items` (GET), `users`, and `reports`. The following routes have **no session/auth check at all** inside their handlers: `customers` (GET/POST/PUT/DELETE), `suppliers` (GET/POST), `restock`, `purchase-orders`, `payments/settle`, `suppliers/settle`, `bills/return`, `cheques/pass`, `cheques/return`, `cheques/by-date`, `items/mixing`. Because `src/middleware.ts`'s matcher only protects page routes (not `/api/*`), any of these endpoints could be called directly (e.g. by a `CASHIER` account or an unauthenticated request with a stolen path) bypassing the UI's role restrictions entirely. This is a genuine security gap, not just a documentation nuance.
- **Staff Management has no edit/delete/deactivate** — `/api/users` only exposes GET and POST; there is no way to change a user's role, disable an account, or remove a user once created, in either the UI or the API.
- **Inconsistent low-stock threshold across the app** — the Reports API hardcodes `stockQty <= 5` for its low-stock section, while the Inventory table and Dashboard use the per-item, admin-configurable `reorderLevel` field. The two "low stock" views can disagree with each other.
- **"Export PDF" is not PDF generation** — `reports/page.tsx`'s `exportPDF()` function is literally `window.print()`; there is no PDF library or server-side rendering involved.
- **Reports pagination is client-side only** — the sub-report tables (stock additions, low-stock, top debtors, cheque report, daily bills, returned bills) are paginated by slicing an already-fully-loaded array in the browser; the API returns the entire dataset for the selected range in one call, which will not scale with data volume.
- **New items are unsellable at correct pricing until first restock** — `AddItemForm.tsx` hardcodes `buyingPrice: 0, sellingPrice: 0` on item creation with an explicit source comment: `// TEMPORARY DEFAULTS (Needed until full FIFO migration)`. A newly registered item has no real price until it goes through the restock flow at least once.
- **shadcn/ui is configured but unused** — `components.json` sets up shadcn conventions, and `class-variance-authority`, `@radix-ui/react-slot`, and `tailwind-merge` are installed, but no actual shadcn component exists in the codebase; this is dead configuration and unused dependency weight (along with the stray `rechart@0.0.1` package).
- **Hard delete only, no cascade definition for customers** — `DELETE /api/customers` performs an unconditional hard delete after a native `confirm()`, with no soft-delete/archival mechanism, and no explicit `onDelete` behavior defined on `Bill.customer` for the case where a customer with existing bills is deleted.
- **Build-time error suppression** — `next.config.js` ignores both ESLint and TypeScript errors during production builds, meaning type errors or lint failures will not block a deploy.
